# OpsBench 001-021 Operations Tool Standards

## Design Goals

The tool surface models a practical operations console rather than exposing
benchmark internals. Every competing Agent for a case receives the same ordered
tool contract from `manifest.yaml`. Frameworks may differ, but tool names,
parameters, execution environment, timeouts, output limits and side effects do
not.

Every invocation writes an independent `tool-<type>-NNN.log` under the run trace.
Outputs are capped at 6000 characters and commands at the case timeout. None of
the tools expose injection code, hidden labels, verifier commands or output,
the Docker socket, the case directory, or the host filesystem.

## 001: `postgres-operations-v2`

The Agent runs in a client container on the database network. PostgreSQL
connection details come from standard `PGHOST`, `PGDATABASE`, `PGUSER` and
`PGPASSWORD` environment variables.

| Tool | Mode | Purpose |
| --- | --- | --- |
| `inspect_database(scope, relation)` | Read | Structured presets for overview, tables, indexes, activity, table statistics and selected settings. |
| `query_database(sql)` | Read/write | Execute intentional SQL diagnosis or DDL/DML repair with `ON_ERROR_STOP=1`. |
| `explain_query(sql, analyze)` | Read | Return JSON `EXPLAIN`; only `SELECT` and `WITH` statements are accepted. |
| `shell(command)` | Read/write | Audited expert fallback, primarily for `psql` and operating-system clients. |

Database tools invoke `psql` with an argument vector rather than interpolating
SQL into a host shell. The database account is the same account granted to all
Agents for this case.

## 002-021: `linux-operations-v2`

The Agent process runs directly in the faulty `target` container. The tools see
the same PID/network namespaces, filesystem, cgroup, loopback interface,
configuration and fault workloads as the affected application.

| Tool | Mode | Purpose |
| --- | --- | --- |
| `read_logs(path, query, tail)` | Read | Discover files under `/var/log`, then filter and tail one log. |
| `inspect_processes(query, limit)` | Read | PID, parent, owner, state, CPU, RSS, age and command line. |
| `inspect_sockets(port, listening)` | Read | TCP/UDP listeners or all sockets with owning process information. |
| `query_host_metrics(pid, sample_seconds)` | Read | Host load/memory plus sampled process CPU cores, RSS, threads and open FDs. |
| `inspect_filesystem(path)` | Read | Byte usage, inode usage, largest children and deleted-but-open files. |
| `probe_http(url, method, body, timeout_sec, ca_file)` | Read/request | Response body, status, latency, remote address and TLS verification result. |
| `inspect_file(path, max_bytes)` | Read | Mode, ownership, size, type and bounded text preview. |
| `edit_file(path, old_text, new_text)` | Write | One exact replacement in a text file up to 1 MB; ambiguous matches are rejected. |
| `manage_service(service, action)` | Read/write | List services or status/start/stop/restart the managed `demo-app`. |
| `shell(command)` | Read/write | Audited fallback for specialized tools such as `flock`, `lsof`, `openssl` and permission repair. |

Structured tools cover the common observation-hypothesis-validation-repair
loop while retaining shell for operations that cannot be represented honestly
by a small generic API. The shell is not a verifier shortcut: it executes only
inside the assigned Agent environment and has no benchmark-control mounts.

## Leaderboard Fairness

- The manifest selects the standard; the Agent implementation cannot request a
  larger tool set.
- `opsbench.cases` rejects a manifest whose ordered tool list differs from the
  registered contract.
- All tool calls share the benchmark timeout and output cap and are recorded in
  the run trace.
- Setup, injection, final verification and cleanup remain benchmark-side phases.
- A PASS still requires both a zero Agent exit code and successful hidden
  verification after the Agent has stopped.
